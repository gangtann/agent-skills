> 本页回答两个问题：Redis 重启后数据从哪里来？为什么生产环境通常 RDB 和 AOF 一起开？
> 读完本页，你应该能做到三件事：
> ① 给定一种持久化配置，说出断电时最多丢多少数据。
> ② 解释 BGSAVE 为什么不会让内存翻倍，以及什么时候会涨得多。
> ③ 预测去掉某个安全步骤（比如先写临时文件）会出什么故障。

# 先看一个具体问题
一台 Redis 写入 QPS 1 万，突然断电。重启后，最后 1 秒、最后 5 分钟的写入还在不在？答案取决于开了哪种持久化、参数怎么配。
Redis 提供两种思路：
- 定期把整个内存拍成快照（RDB）。
- 把每一条写命令追加到日志（AOF）。
下面先看两者的骨架，再分别往下钻。

# 两种方式对比
下表是两种方式的核心差异：
| 维度 | RDB | AOF |
|---|---|---|
| 存什么 | 某一时刻的全量快照 | 每条写命令 |
| 触发 | `save` 配置 / `BGSAVE` | 每次写命令后追加 |
| 断电最多丢 | 上次快照之后的全部写入 | 取决于 `appendfsync`，通常 ≤1 秒 |
| 关键源码 | `src/rdb.c` `src/server.c` | `src/aof.c` |
| 主要代价 | fork 时的内存与停顿 | 文件膨胀，需要重写 |
可以看到两者的弱点正好互补，这就是生产上常一起开的原因。

# RDB：fork 出来的快照
自动快照由 `save <秒> <次数>` 配置触发，比如 `save 300 10` 表示「300 秒内至少有 10 次写入」才执行一次 `BGSAVE`；条件不满足就不会拍快照。
`BGSAVE` 的控制流骨架如下，先看全貌：
```
rdbSaveBackground()                  # src/rdb.c
    pid = fork()                     # 子进程共享父进程内存页（copy-on-write）
    if pid == 0:                     # 子进程
        rdbSave(...)                 # 遍历所有 db，序列化到临时文件
        rename(tmpfile, "dump.rdb")  # 原子替换，避免读到半个文件
        exit
    else:                            # 父进程继续服务请求
        记录 child_pid，稍后在 serverCron 里回收
```
有了骨架，再看两个容易误解的细节。

## 为什么不会把内存翻倍
fork 之后父子进程共享物理页，只有父进程修改某一页时，内核才复制那一页。所以额外内存取决于快照期间**被写到的页数**，不是数据总量。写入越密集，复制的页越多。

## 为什么要先写临时文件
如果直接覆盖 `dump.rdb`，写到一半宕机就会留下一个损坏文件，连旧快照也没了。先写临时文件再 `rename`，任何时刻磁盘上都有一份完整快照。

# AOF：追加日志与重写
知道了 RDB 会丢最后一段写入，下一个问题是 AOF 怎么把丢失窗口压到 1 秒左右。关键是 `appendfsync` 的三种取值：
1. `always`：每条命令都 fsync，最安全也最慢。
2. `everysec`：后台线程每秒 fsync 一次，默认值，最多丢约 1 秒。
3. `no`：交给操作系统决定，丢失窗口不可控。
AOF 的问题是文件只增不减。对同一个 key 执行一万次 `INCR`，日志里就有一万行。`BGREWRITEAOF` 同样借助 fork，由子进程按当前内存状态重新生成一份最小命令集。
> 注意：常见的误解是「AOF 重写会读取旧 AOF 文件」。实际上重写依据的是内存中的当前数据，不读旧日志。

# 自测题
读完本页，试着不看文档回答。每道题对应开头的一个要点，题后括号里是答案所在的小节。
1. 配置了 `save 300 10`、没开 AOF。最后一次快照在 4 分钟前，之后写了 8 次，然后断电。重启后这 8 次写入还在吗？如果改成开了 AOF 且 `appendfsync everysec` 呢？（两种方式对比；AOF）
2. 一个 50GB 的实例执行 `BGSAVE`，监控显示内存只涨了 3GB。这正常吗？什么样的业务负载会让它涨得更多？（为什么不会把内存翻倍）
3. 有人为了省磁盘空间，把快照改成直接覆盖写 `dump.rdb`。描述一个会因此丢失全部数据的具体场景。（为什么要先写临时文件）
# 参考答案
> 先自己答，再往下看。
1. 不在。RDB 只在满足 `save` 条件时生成快照，4 分钟内只写了 8 次，没达到「300 秒内 10 次」，所以最后一次快照之后的写入全部丢失。开了 AOF 且 `everysec` 时，每条写命令都追加到日志，后台每秒 fsync 一次，所以最多只丢断电前约 1 秒内的写入，这 8 次基本都在。
2. 正常。fork 之后父子进程共享物理页，只有父进程修改某一页时内核才复制那一页（copy-on-write）。所以多出来的内存等于快照期间被写到的页数，跟数据总量无关。写入越密集、越分散（大量随机 key 被修改），被复制的页越多，内存涨得越多。
3. 快照写到一半时进程崩溃或机器断电：旧的 `dump.rdb` 已经被覆盖了一部分，新的又没写完，磁盘上只剩一个损坏的文件。重启后 Redis 无法加载，等于丢失全部数据。先写临时文件再 `rename` 时，`rename` 是原子操作，任何时刻磁盘上都有一份完整的快照。
